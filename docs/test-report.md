# AI Anchor 测试报告

每一阶段测了什么、在真机上看到了什么、还有什么没测到。新的在前，旧的在后。项目说明、安装和用法见 [README](../README.md)。

章节名前面的是开发阶段：

- **P0**：命令行原型，在一台 Windows 电脑上做到“AI 程序走固定出口且不泄露”。
- **P1a**：变成常驻后台：登录后自动运行，内核崩溃自动恢复并记进时间线，应用更新后守卫规则自动覆盖新版本。
- **P1b**：出口核对与锁定、断联采集与归因、线路控制器、备用出口。设计决定见 [p1b-decisions.md](p1b-decisions.md)。
- **P1c**：一致性检测、久未恢复的提醒。
- **门槛 2**：P1 到 P2 的验收，一周内每次断联都有归因、“未知”低于 10%，结果见下面“门槛 2 的结果”。
- **P2**：原定目标是云端锚点（把 AI 会话放到服务器上运行，本地断网时不中断），还没有开始。先做了面板，之后是一条命令升级、升级特权服务、CI、升级后退回、面板里直接操作、首次安装、卸载。

每次推到 `main`、每个 PR，GitHub Actions 都在 Windows 上编译整个工作区并跑单元测试（`cargo build --workspace --locked`、`cargo test --workspace --locked`，见 `.github/workflows/ci.yml`）。端到端测试和真机实测不在里面：它们要 sing-box、真的网卡和已安装的服务，仍然是手动做的，结果记在下面各节。

## P2 · 卸载

原来没有卸载命令，要手工做四步：`anchor service uninstall`、`anchor agent uninstall`、删安装目录、从 PATH 里去掉那一项。而 `anchor service uninstall` 会把防火墙守卫规则留着，只照着做的话，AI 程序之后一直只能连本机。现在是一条命令：`anchor uninstall`。

- `cargo test --workspace`：218 个单元测试（上一节是 210 个）。新增 8 个：
  - 卸哪个目录：`--to`、运行中的用户代理所在的目录、登录自启、默认位置，依次往后找；都没有就拒绝，不猜本程序所在的目录
  - 不像安装目录的拒绝：不存在、没有程序、是编译目录
  - 只删 AI Anchor 放的文件：三个程序、`.old` / `.new`、上一版目录里的这些和 `replaced-by.txt`；用户的 `.bak`、别的文件和子目录都不碰，上一版目录里多出来的文件也不碰。本程序自己留到退出后再删
  - 只有 AI Anchor 的文件时，删完连目录（和上一版目录）一起删掉
  - PATH 里去掉安装目录：写法不同也认，出现几次去掉几次；别的项、空项、结尾的分号原样留着；只是前缀相同的不算
  - 写回注册表时类型不变（REG_SZ、REG_EXPAND_SZ 都试了）；没有可去的就不写；读不懂的值原样留着并报错
  - 登录自启只在指向这个安装目录时删；指向别处的、不是本程序写的格式的都不动
  - 快捷方式只认指向这个目录里 `anchor.exe` 的
- 写注册表的那两个测试用的是临时的键（`HKCU\Software\AIAnchorTest-…`，测完删掉），不是用户的 PATH 和登录自启。
- 端到端（本机，临时目录里；调试版本）。25 项检查全部通过：
  - 测试脚本的规定：会改动的命令一律带 `--keep-guard`（不动特权服务和守卫规则，隐藏的测试用选项）和 `--shortcut-dir`（在临时目录里找快捷方式，代替桌面），不带就中止；终端不能是管理员；开始前把用户的 PATH 原文存到一个文件里备用
  - 开头先预览，确认命令指向的是临时的安装目录，不是真机的；对不上就中止。预览里看得到：会停掉从这个目录运行的用户代理；真机的登录自启“指向别处，不动”；真机桌面上没有指向这个目录的快捷方式；不带 `--keep-guard` 时，特权服务“已安装，会停止并删除（要管理员确认）”、守卫规则“2 条，会删除”（只预览，从没执行）
  - 拒绝：编译目录、不存在的目录、不是安装目录的目录
  - 回答 n：什么都没动，用户代理还在
  - 用安装目录里的 `anchor.exe` 卸载它自己所在的目录（里面有上一版、一个用户自己的文件，有一个用户代理在运行，临时目录里有两个快捷方式）：用户代理停了；只删了指向这个目录的那个快捷方式，另一个留着；正在运行的 `anchor.exe` 在命令结束后被删掉；AI Anchor 的文件都没了，用户的文件和目录留着
  - 从编译目录运行、用 `--to` 卸一个只有程序的目录：目录当场删掉
  - 用目录里的 `anchor.exe` 卸它自己、目录里只有程序：命令结束后整个目录被删掉
  - 都卸完之后再运行：找不到安装目录，拒绝并提示 `--to`
  - 测试前后，真机的安装目录、特权服务（程序、状态、进程）、守卫规则条数、用户代理进程、登录自启、桌面上的快捷方式、注册表里用户的 PATH 都没有变，没有留下测试用的注册表键
- “首次安装”的端到端测试重跑了一遍（这次把写 PATH 的那一步拆成了单独的函数，卸载也用它）：25 项检查全部通过。
- 尚未实测：
  - **删特权服务和守卫规则的那一步从来没有执行过。** 它是新加的 `anchor-svc uninstall --remove-rules`：删服务的部分和原来的 `anchor service uninstall` 是同一段代码，删规则的部分和 `anchor guard remove` 是同一段代码（这次把它拆成了单独的函数，两边共用）。但这两件事接在一起、以管理员身份跑一遍，测试里不能做（会动真机的服务和规则），真机上也还没有做过。取消管理员确认时“别的都不动”也只看了代码。
  - 真的从用户的 PATH 里去掉一项：只在临时的注册表键上测过。
  - 删真的桌面快捷方式：测试里用的是临时目录。
  - 在真机上完整卸载一次。release 版本。

## P2 · 首次安装

第一次安装原来是手工的：编译，把三个程序复制到某个目录，再自己把它加进 PATH；README 里连复制到哪里都没写。现在是一条命令：运行新编译出来的 `anchor.exe install`。

- `cargo test --workspace`：210 个单元测试（上一节是 203 个）。新增 7 个：
  - 装进一个还不存在的目录：三个程序都在，不留 `.new`，别的文件不带；没有编译服务程序时装两个
  - 不是第一次安装的都拒绝：本程序旁边不是完整的一套；目标目录里已经有其中一个程序（提示用 `anchor upgrade`，什么都不动）；目标就是本程序所在的目录
  - 装到一半出错：这次放进去的都拿掉；目录原来不存在的连目录都不留，原来就有的只留下原来的文件
  - PATH 里的一项怎么算“已经有了”：不分大小写，不管末尾的反斜杠、引号、正斜杠，写成 `%变量%` 的也认，只是前缀相同不算。往末尾加的时候原来的内容一个字都不改，原来以分号结尾就不多加一个
  - 写注册表：原来没有 Path 时新建；原来是 REG_EXPAND_SZ 或 REG_SZ 的，类型不变，原来的内容原样在前面；已经在里面的不动
  - 读不懂的 Path（不是文字类型、不是合法的 UTF-16）原样留着并报错；目录名里有分号时拒绝
  - 装完之后列出的步骤：已经有的 sing-box 和配置标出来；不在 PATH 里时写明完整路径
- 写注册表的那两个测试用的是一个临时的键（`HKCU\Software\AIAnchorTest-…`，测完删掉），不是用户的环境变量。读写的代码是同一段，只是键由调用方给。
- 端到端（本机，临时目录里；调试版本）。25 项检查全部通过：
  - 开头先用预览确认命令指向的是临时目录，不是真机的安装目录；对不上就中止
  - 预览：列出三个程序和 PATH 那一行，什么都不建
  - 装到默认位置（把 `LOCALAPPDATA` 指到临时目录）：三个程序和编译结果一致，目录里没有别的；装好的 `anchor.exe` 能运行；结束时列出剩下的步骤，并写明不在 PATH 里时怎么调用
  - 再装一次：拒绝，提示用 `anchor upgrade`，什么都没变；预览同样拒绝
  - 装出来的目录 `anchor upgrade --to … --dry-run` 认得，三个文件都是“没有变化”
  - `--to` 一个名字里带空格的目录；一个已经存在、里面有别人文件的目录（那个文件原样留着）
  - 装到编译目录自己、`anchor.exe` 旁边没有别的程序：拒绝
  - 测试前后，真机的安装目录、注册表里用户的 PATH 都没有变，没有留下测试用的注册表键
- **PATH 那一步在端到端测试里只做了预览。** 用户的 PATH 在注册表里，没法指到别处去，所以测试脚本规定：会改动的命令一律带 `--no-path`，不带就中止。预览时它读的是真的 PATH（只读），对一个不在里面的目录给出了“在末尾加上安装目录”。
- 真机实测（2026-11-25，release 版本，用新编译的 `anchor.exe upgrade` 装上）。真机早就装好了，所以这里能看到的只是“已经装过时它怎么做”，以及这次升级本身：
  - 运行之前预览（只读）：新编译的 `anchor.exe install --dry-run` 拒绝，写明“已经装过了，没有做任何改动”，并给出完整的升级命令。
  - 装上之后预览（只读）：装好的 `anchor install --dry-run` 拒绝，写明安装目录就是它自己所在的目录、换新版本要运行新编译出来的那个 `anchor.exe upgrade`。
  - 前后核对：注册表里用户的 PATH 没有变。
  - 这次升级里服务程序没有变化（代码没动，编译出来的文件和装着的一样），是“三个文件里有一个没变”第一次在真机上出现：变了的两个换成了新的；没变的那个内容和修改时间都和原来一样，没有被碰；`previous\` 里仍然是完整的三个程序加 `replaced-by.txt`，三个都和升级前记下的校验值相同。
  - 用户代理换了一个进程，从断开到放行 11 秒，拦下 10 次 AI 连接。比平常的 5 秒左右长：内核启动后前三次出口核对都是连接超时，第四次才一致。同一天早些时候线路有过一次 6 分钟的锁住（日志归到 VPN 隧道卡住），所以判断是线路当时不稳；这是推断。
  - 第一次运行升级命令没有生效：之后核对时三个程序、`previous\`、用户代理进程都和之前一样，日志里没有重启的记录，也没有留下 `.new` 或 `.old`。没有拿到那次的终端输出，分不出是没有运行，还是在停用户代理之前就出错了。再运行一次就成了。
- 尚未实测：
  - 真的往用户的 PATH 里加一项，以及加完之后新开的终端认不认得 `anchor`：没有做过。读写的代码只在临时的注册表键上测过（本机和 CI 都通过）。
  - 在一台没装过的电脑上从头走一遍 README 的[“快速开始”](../README.md#快速开始)。
  - `anchor install` 用 release 版本真的复制程序。

## P2 · 面板里直接操作

面板原来只能看状态和做托盘菜单里已有的几件事，换线路、换出口、登记基线都要开终端敲命令；每点一次托盘图标还会多开一个窗口。这次把这三件事接到面板上，并且让已经开着的窗口被找回来。

- `cargo test --workspace`：203 个单元测试（上一节是 198 个）。新增 5 个：
  - 登记基线的按钮只在出口 IP 变了、或者还没有基线时出现；回显服务连不上、内核没在运行、配置有误、线路都不通时不出现。这两种情况下的建议里写着按钮，也留着命令
  - 线路一栏的内容：没有配置线路时没有这一栏；每条线路的状态和文字；固定、所有线路都不可用时的说法
  - 出口一栏：只有一个出口时没有这一栏；名字不在说明里重复
  - 换出口只接受配置里有、而且不是正在用的名字：不认识的、正在用的、后面粘着选项的、以 `-` 开头的都拒绝
  - 哪些窗口算“开着的面板”：标题对、是 Edge 的窗口才算；还没读到状态或会话失效的、普通浏览器里的标签页、别的程序的窗口都不算
- 端到端（本机隔离目录：两条线路、一个主出口加一个备用出口，都是本机的 sing-box；python 充当 IP 回显服务；用户代理不带托盘，三个标准输入输出都指向 NUL，和 `anchor agent start` 启动的一样）。调试版本，36 项检查全部通过：
  - 面板拿到的数据：两条线路（当前的是第一条）、两个出口和各自的基线；通道放行时没有登记基线的按钮
  - 换线路：点了之后面板和 `anchor line list` 都显示换过去了。固定、取消固定同样
  - 不认识的线路名：拒绝，原因是线路控制器给的（“没有叫 … 的线路”）；没写名字、名字长得离谱：拒绝
  - 换出口：不认识的、正在用的、后面粘着 `--yes` 的名字都拒绝，也没有打开窗口。合法的名字：打开了一个运行 `exit use backup` 的命令窗口，命令行里没有 `--yes`；6 秒后它还在等回答，这期间出口没有换
  - 登记基线：把回显的 IP 换成另一个，通道锁住，面板拿到“该显示按钮”；点了之后打开一个运行 `baseline` 的命令窗口，6 秒后还在等回答，这期间配置文件没有变。IP 换回去之后通道放行，按钮消失
  - 新加的操作和原有的一样受保护：来源不对 403，没有令牌 401，普通表单 415，而且都没有产生效果
  - 测试前后，真机的配置文件和出口选择没有变
- 在浏览器里看（Claude 桌面版内置的浏览器，窗口宽 460，接的是同一个测试用的用户代理）：“线路”“出口”两栏排版正常；点“换到这条”，当前的标记换到了另一条；把回显的 IP 换掉之后，最上面出现“登记现在的出口为基线…”。
- 原有的面板端到端测试重跑了一遍，结果和之前一样。
- **顺带发现并修掉的一个老问题：从面板或托盘菜单打开的命令窗口可能一闪就关。**
  - 用 `anchor agent start` 或 `anchor upgrade` 启动的用户代理，标准输入输出都指向 NUL。它再去开命令窗口时，这三样被原样传了下去：窗口里什么都不显示，等回车的地方读到的是“输入结束”，窗口马上关掉。登录时自动启动的用户代理没有这三样，不受影响。
  - “运行体检”“完整报告”“完整时间线”一直是这样开窗口的，所以这个问题在这次改动之前就有。它在真机上有没有出现过，没有记录。
  - 现在开命令窗口的那一下不再传这三样，新窗口用它自己的控制台。
  - 前后对照（同一个端到端测试，只差这一处修改）：没改时，“登记基线”的命令窗口 1.5 秒内就退出了；改了之后停在那里等回答。“换出口”的那个窗口在 1.5 秒时两种情况下都还在（它要先查正在运行的 AI 程序），所以对照只在“登记基线”上看得出来。
- 真机实测（2026-11-24，release 版本，用 `anchor.exe upgrade` 装上；用户代理是升级命令启动的，正是命令窗口原来会出问题的那种情况）：
  - 升级本身和往常一样：之后核对（只读），三个程序和编译结果一致，`previous\` 里是换下来的那一版；用户代理重启，AI 通道从断开到放行 5 秒左右，拦下 2 次 AI 连接。
  - 命令窗口：在面板里点“运行体检”之后，那个命令窗口一直开着等回车，几分钟后核对时进程还在。窗口里的内容显示得是否正常，没有记录。
  - 面板窗口的标题：读了真机上开着的面板窗口，是 Edge 的窗口，标题是“AI Anchor · 已放行”，和代码里找的一致。这是之前唯一没有在真的 Edge 上验证过的假设。
  - 窗口只开一个：面板开着的时候再运行一次 `anchor panel`，用户代理的日志里记下“面板窗口已经开着，切到前面”，面板窗口仍然只有一个。
  - 再点一次托盘图标的那条路：操作的人说窗口被切到了前面；但当时日志里没有对应的那一行，所以没有把它算作验证过。点托盘图标和 `anchor panel` 调用的是同一个函数。
  - 真机的面板上没有“线路”“出口”两栏，也没有登记基线的按钮：没有配线路和备用出口，出口 IP 也没有变。
- 尚未实测：
  - 真机上的换线路、换出口、登记基线：真机没有配线路，也没有备用出口，登记基线的按钮要等出口 IP 真的变了才会出现。
  - “切到前面”的几种情况：面板窗口最小化时的还原；面板窗口在别的窗口后面时，从终端运行 `anchor panel` 能不能真的把它拿到最前面（真机那次它本来就在最前面）。
  - 命令窗口里真的回答 y：测试里只让它等着，然后结束它。`anchor exit use` 和 `anchor baseline` 本身的测试见各自的章节。

## P2 · 升级后退回

升级成功之后旧文件原来是直接删掉的，新版本用着不对也没有办法回到上一版。现在升级时把换下来的那一版留在安装目录的 `previous\` 里，`anchor upgrade --rollback` 把它换回去。退回走的就是升级的那段代码（来源换成 `previous\`），所以停、换、启动、起不来换回都不用另写。

- `cargo test --workspace`：198 个单元测试（上一节是 193 个）。新增 5 个，都在换文件这一层，不涉及用户代理：
  - 换下来的那一版完整留下（没变的程序也留一份，别的文件不留），退回之后安装目录是上一版、`previous\` 里是刚才那一版，再退一次换回来
  - `previous\` 不能用的四种情况都拒绝：还没升级过；升级之后安装目录被手工换了一个文件；没有 `replaced-by.txt`；缺一个程序。被手工改过时，错误里写着怎么手工装 `previous\` 里的那一份
  - 升级中途换回时，复制到一半的那一份删掉，`previous\` 里原有的上一版不受影响、仍然能退回；原来没有 `previous\` 时不留空目录

## P2 · 升级特权服务

## P2 · 一条命令升级

每次装新版本都要在终端里敲四条命令（停用户代理、复制两个程序、启动用户代理）。`anchor upgrade` 把它们合成一条，并且在新程序起不来时自己换回去。

- `cargo test --workspace`：183 个单元测试（改锁住时长的算法时是 175 个）。新增 8 个：
  - 从哪里装到哪里：没写目录时装到用户代理所在的目录，它没运行就看登录自启，都没有就报错；写了目录就装到本程序所在的目录；`--to` 最优先；两边是同一个目录时拒绝（不分大小写，不管末尾有没有反斜杠）
  - 登录自启那一行的解析，不是本程序写的格式不认
  - 比较内容：长度相同、内容不同也算变了；新程序目录不完整、安装目录不像安装目录时拒绝
  - 复制、换上、换回、删旧文件：复制完之前不动正在用的文件；别的文件不碰；上次留下的 `.old` 先清掉
  - 换到一半有一个文件改不了名（被别的程序独占打开）：已经换上的换回去，不留 `.new` 和 `.old`
  - 复制失败（计划之后新程序少了一个）：什么都不留
  - 特权服务的提示：只在装了服务、而且和新编译的不是同一个文件时出现（提示的文字在“升级特权服务”那次改过）
  - 按进程号找程序路径、等进程退出
- 端到端（本机：在临时目录里放一个“安装目录”，里面是真机现在装的那一版的副本；python 充当 IP 回显服务，另一个 sing-box 充当出口，用户代理不带托盘）。调试版本和 release 版本各跑一遍，release 那次 62 项检查全部通过：

  - 运行新编译的 `anchor.exe upgrade`，不写安装目录：从运行中的用户代理找到安装目录；两个程序换成新的，`anchor-svc.exe` 新增；用户代理换了一个进程、仍然从安装目录运行、保留了 `--no-tray` 和数据目录；不留 `.new` 和 `.old`；AI 通道重新放行。中间停了 1.5～2.9 秒
  - 再运行一遍：“已经是这个版本，没有改动”，用户代理不重启
  - 只有 `anchor.exe` 不同：只换它，用户代理不重启
  - 用安装目录里的 `anchor.exe` 升级它自己（`anchor upgrade <目录>`）：两个程序都换成新的，自己的旧文件留作 `anchor.exe.old`，换上的 `anchor.exe` 能运行；下一次升级时 `.old` 被删掉
  - 新的用户代理起不来，三种情况：刚启动就退出、文件根本不是程序、启动了但一直不应答（15 秒后结束它）。三种都以失败结束，两个程序换回原样，原来的用户代理重新启动（一个进程，没有多余的），AI 通道重新放行。前两种不到 3 秒，第三种 17 秒左右
  - `--to` 指向的目录不是用户代理所在的目录：拒绝，那个目录不动
  - 用户代理没在运行：只换文件，不启动它
  - 用户代理没在运行、又没写 `--to`：拒绝，提示用 `--to`。这台电脑上登录自启指向的是正式的数据目录，和测试用的数据目录不同，所以没有被采用
  - 目录不是编译好的程序目录：拒绝

## P2 · 锁住的次数和时长

做“按钟点看”时发现：报告和面板里“AI 通道锁住 N 次，共多久”原来是把每次放行时记下的时长加起来，会少算。锁着的时候用户代理重启过（或者电脑没关好就断电、睡眠），放行时只记了重启之后的那一段；锁着时退出用户代理的那一次没有放行，不计。

改成按锁住的时段算，和“按钟点看”同一个口径（以有探测记录的时间为上限）。面板里“最近 24 小时每小时锁住多久”的图也改成同一个口径，小时改按本机时区的整点分。

- `cargo test --workspace`：175 个单元测试（加按钟点看时是 174 个）。新增和修改的覆盖：
  - 一次正常的锁住、一次锁着时断电再开机、一次锁着时退出用户代理：次数算 3 次，时长包括重启前锁着运行的那一段、不包括关机的那几个小时，原因里多一项“没等到放行”
  - 探测明细留不到的更早时段仍然用放行时记下的时长；完全没有探测记录时和原来一样
  - 24 小时的图：电脑睡着的那个小时不算锁住，只运行了 20 分钟的小时最多算 20 分钟；探测明细留不到的小时不设上限；时区不是整小时时按本地整点分
  - 还留着的最早一条探测的时间（时间线新增的查询）
- 用真机的时间线核对（只读），同一份数据，装着的旧版本和新版本各跑一遍 `anchor report`：

  | 时段 | 原来 | 现在 |
  |---|---|---|
  | 24 小时 | 10 次，共 7 分 53 秒 | 10 次，共 8 分 3 秒 |
  | 7 天 | 76 次，共 3 小时 23 分 | 78 次，共 7 小时 55 分（多出的 2 次是“没等到放行”） |
  | 30 天 | 103 次，共 3 小时 32 分 | 111 次，共 8 小时 5 分 |

  7 天里多出来的 4 个半小时，主要是 11-16 夜里那一次：锁住后用户代理又运行了 4 个多小时，之后没有正常退出，重新启动后 85 分钟才放行，放行时只记了这 85 分钟。平时没有重启的日子，两种算法差不多（24 小时那一行只差 10 秒）。
- 面板的端到端测试重跑通过；“24 小时”的锁住时长和每小时的图加起来现在对得上，最多差 1 秒（调试版本那次都是 25 秒，release 版本那次是 25 秒和 26 秒；原来一个 23 秒一个 25 秒）。差的 1 秒是取整的方式不同：总时长舍去不满 1 秒的部分，图上每个小时四舍五入到秒。
- 真机实测（2026-11-22，装上这一版之后）：
  - 安装目录里的两个程序和编译结果一致（SHA256 相同），用户代理重启后正常，日志里没有异常。
  - 用安装目录里的 `anchor.exe` 跑 `anchor report --since 7d`：锁住 81 次，共 7 小时 56 分 19 秒（出口不可达 52、网络变化 14、内核启动 13、没等到放行 2）。安装前用同一版本算的是 78 次、7 小时 55 分 33 秒；多出的 3 次、46 秒，和安装后 90 分钟里的记录对得上（重启用户代理 1 次，出口短暂断开 2 次，共 45 秒，差的 1 秒是取整）。
  - 面板“7 天”里“AI 通道锁住”一格显示的次数和时长与上面一致，原因里有“没等到放行”（操作的人确认）。
- 尚未实测：
  - 统计超过 7 天时，更早那一部分仍用放行时记下的时长（见 README 的[“已知限制”](../README.md#已知限制)）；这部分少算多少，没有办法用现有数据核对。
  - 装上之后还没有出现过“锁着时用户代理重启”或“锁着时退出”的情况；这两种情况只有单元测试和对旧数据的重算。

## P1c · 丢包和孤立超时的归因

起因是门槛 2 报告里“未知”集中在 11-21 一天。直接读真机的时间线（只读），把 8 天里 18 次“未知”前后 45 秒的探测逐条列出来看：

- 17 次是同一种：经出口连接 `api.anthropic.com`（1 次是 `bridge.claudeusercontent.com`）超时。另 1 次是连接一个 IPv6 地址时系统报“参数无效”，发生在一次 VPN 卡住的开头。
- 这 17 次里，16 次的突发探测在 2～11 秒后经出口访问同一个域名是通的（拿到了 HTTP 响应），官方状态页也没有报严重故障；剩下 1 次没有重复探测（它紧跟在另一次超时后面，那一次的探测 2 秒前刚测过，是通的）。所以不是服务端的问题，也不是出口断了。
- 其中 5 次，断联前后 10～15 秒内有经 VPN 上网的探测“第一次失败、重试才成功”。这种探测原来算成功，归因时看不出来。
- 另有几次只是探测明显变慢（经 VPN 上网 1.5～2.6 秒，平时 0.2 秒；整条链路 3.7～4.4 秒，平时 0.5 秒），或者重试、失败发生在 10 秒以前。这些没有纳入规则：慢多少算异常没有依据，10 秒以前的按原来的决定不算到这一次头上。

据此加了两条规则，都排在原有各条之后，原来能归因的不受影响：

- **探测要重试才成功**：断联前 10 秒到之后 15 秒内，哪一段的探测要重试才成功，就归到哪一段。经 VPN 上网的（且绕开 VPN 能上网）归“VPN：隧道在丢包”；整条链路的归“出口：这条路在丢包”；路由器、绕开 VPN 的归“本地”。
- **孤立的一次超时**：连接超时，前后经出口访问同一个域名是通的，各段探测也正常，归“出口：一时的丢包”。依据里写明分不出是在 VPN 隧道里还是在出口到 AI 服务之间。没有这个域名的探测结果、或者不是建立连接时的超时，仍然是“未知”。

第二条的依据比第一条弱：它只排除了本机网络和服务端，没有直接看到丢包。这样归的理由是：连接是从出口发出去的，本机网络当时验证过是好的，同一个域名随后可达，剩下的只有出口这条路；原有规则对“各段正常时的 DNS 失败”也是这样处理的。

- `cargo test --workspace`：172 个单元测试（加面板时是 171 个）。新增的一个测试覆盖：都正常且没有该域名的探测时仍是未知；经 VPN 的探测要重试归 VPN；没有绕开 VPN 的数据或不经 VPN 时只说本地；路由器、宽带由近到远；整条链路要重试归出口；10 秒以前和 15 秒以后的不算；断联那一刻明确失败的仍按原来的说法；孤立超时归出口，有没有 VPN 两种写法；探测的是别的域名、该域名不通（归服务端）、不是超时、不是建立连接时出的错，都不套第二条；DNS 失败时 VPN 在丢包说 VPN。
- 用真机的时间线回放（只读，新增一个手动运行的测试 `reattribute_a_real_timeline`）：8 天里没被锁住拦下的 172 次断联用新规则重新归因。原来归“出口”20 次、“本地”36 次、“VPN”98 次的全部不变；18 次“未知”里 5 次改归“VPN”（探测要重试），12 次改归“出口”（孤立超时），1 次仍是“未知”（IPv6 那次）。按这个结果，这 8 天的“未知”是 219 次里的 1 次。锁住期间拦下的 47 次没有重算：记录里没有锁住的起止时间。
- 尚未实测：新规则只在历史数据上回放过，装上之后新发生的断联还没有按它归因过。

## P1b · 出口核对与锁定

- `cargo test --workspace`：128 个单元测试（P1a 是 57 个）。新增的覆盖：
  - 状态机：内核启动先锁、一个来源一致就放行；定时核对要两个不同来源才锁；第二个来源一致就撤销怀疑；网络变化先锁后核对；锁住时立刻换来源确认；回到基线自动放行并通知；出口不可达时先锁、30 秒后放慢重试、不发“无法核对”；回显服务持续失败 20 秒才算无法核对且只通知一次；只有一个来源时可以自己确认；地址族不同不作判断
  - sing-box 配置：以 Lock 模式启动、只锁 AI 入站、Open 在模式列表里、不开 `cache_file`；探测入站带账号密码
  - 网络变化：订阅和取消；只看会影响出口的地址和默认路由
  - 配置：探测端口与其他端口冲突、`exit_check_interval` 格式、`probe_url` 必须是 https、带 BOM 的 `anchor.toml`
  - 管道名按数据目录区分；托盘、`anchor status`、`anchor check` 里的锁定提示；新事件的时间线描述
- 先单独用 sing-box 1.14.4 验证了做法：Lock 模式下 AI 入站的 HTTP 请求立即 502、HTTPS 立即断开；探测入站不带账号密码返回 407；`PATCH /configs` 切换 1～2 毫秒生效；开着 `cache_file` 时重启会沿用上次的模式（所以不开）。
- 端到端：用户代理以 `--no-tray` 运行，数据目录、端口都与正在用的那套隔开；本机 python 充当 IP 回显服务，另一个 sing-box 充当可以停掉的出口。
  - 启动：锁住 1.8 秒后核对通过放行，AI 端口可用。
  - 回显到的 IP 改成别的（对应 T5b）：14.7 秒锁住（5 秒定时核对 + 10 秒换来源确认），AI 端口返回 502，`anchor check` 归因到出口。
  - 改回基线后 `anchor exit check`（对应 T5c）：自动放行，记“出口恢复”。
  - 出口不变时 `anchor exit check`（对应 T5d）：锁住 8 毫秒后放行。
  - 强制结束内核：重启后锁住 263 毫秒，核对通过放行。
  - 回显服务返回乱码、出口能连通：22 秒后“无法核对”，保持锁住；恢复后放行。
  - 停掉出口：4.9 秒锁住（出口不可达）；出口恢复后 2.1 秒核对通过放行。
  - 退出后没有残留的 sing-box。
  - 端到端里有两次 AI 端口请求在放行后失败，日志显示请求已被放行，是测试出口经 VPN 访问外网时 10 秒超时，与锁定无关。
- 测试中发现并修复：ureq 经 HTTP 代理访问 http:// 地址时不带 `Proxy-Authorization`（只有 CONNECT 才带），探测入站因此一直返回 407、通道一直锁住。改为经 SOCKS5（带账号密码）访问探测入站。
- 真机实测（全量 VPN 的专属 IP，出口直连并绑定 VPN 网卡），第一版：
  - 安装后用户代理启动，核对通过放行；托盘显示“运行中 · 出口 <基线 IP>”。
  - **T5a 切到别的服务器**：断开时就已锁住，新隧道建好 4 秒后两个来源确认出口已变化（另一台服务器的 IP），弹出通知。新 IP 上没有 AI 请求发出。
  - **T5c 切回专属 IP**：自动放行并通知，但在隧道恢复 15 秒后才放行，超过 10 秒的目标。原因：隧道刚恢复时第一次核对失败，“已变化”状态按 10 秒重试。
  - **T5d 断开再连回同一台**：隧道恢复 5 秒后放行，超过 3 秒的目标。原因：一次网络变化带来一串通知，每条都让进行中的核对作废，新核对要等旧的超时。

- 据此修改（第二版）：网络变化、内核启动后 30 秒内，锁住的各种状态都快速重试；收到网络变化就丢掉进行中的核对，等通知平息 0.5 秒再核对；回显超时从 6 秒降到 4 秒，锁着时同时测出口本身通不通；锁着时每次核对结果都写进 `agent.log`。
- 第二版真机实测（时间从最后一条网络变化通知算起）：
  - 启动：锁住 1.3 秒（第一版 16.9 秒）。
  - **T5c**：隧道恢复 6 秒后放行（第一版 15 秒），达标。
  - **T5a**：隧道恢复 8 秒后确认出口已变化并通知，期间一直锁住。
  - **T5d**：隧道恢复 6 秒后放行，仍超过 3 秒。日志显示隧道刚恢复时 sing-box 的连接 0 毫秒就失败（“网络不可达”），程序却要等“出口通不通”的测试满 3 秒超时，再隔 2 秒才重试。
- 第三版：回显请求拿到了响应（状态码或内容不对）就认定出口能连通，不再测；连接没建立时，最多再等出口测试 1 秒；快速重试间隔从 2 秒降到 1 秒。本机端到端复测通过：出口恢复后 1.1 秒放行（第二版 2 秒）。
- 第三版真机实测 **T5d**：最后一条网络变化通知后 9 秒放行。内核日志显示隧道路由回来后，头 2 秒连接 0 毫秒就失败（网络不可达），接着一次连接卡住、4 秒后超时（路由在、流量还过不去），下一次才成功。隧道真正可用的时刻在通知后 2～7 秒之间。瓶颈是同一时间只跑一个核对，卡住的那个把下一次尝试推迟了。
- 第四版：锁着时，进行中的核对超过 1 秒没结果，就换一个来源并发一个，最多 3 个，谁先确认一致谁放行；状态一变（放行、确认已变化），其余并发的核对结果全部丢掉，迟到的失败不会把刚放行的通道再锁上。本机端到端新增场景：先问到的回显服务卡住 8 秒时，1.06 秒放行（不并发要 5 秒以上）。
- 第四版真机实测 **T5d**：VPN 关掉约 40 秒再连回同一台。最后一条网络变化通知后 5 秒放行；其中头两次核对仍然失败（隧道还过不去），隧道可用后 1～2 秒内放行。按“隧道可用后多久放行”算达标；从通知算起的剩余几秒是 VPN 客户端自己接通隧道的时间。VPN 关着的 43 秒里，锁住的前 30 秒每秒核对一次，之后放慢到 5 秒一次。
- 真机上还记到一次放行期间的短暂断联：定时核对时出口不可达，先锁住，3 秒后核对一致放行。
- 真机时间线（装上 DNS 修复之前的 15 小时）：放行期间 11 次“出口不可达”锁住，大多 2～3 秒，两次 2 分钟多。错误都是经出口的连接 4 秒没建立，原因是当时 DNS 在超时（见下面“direct 出口的 DNS”）。DNS 修复后 2.7 小时里 0 次。
- 装上断联归因版本后 52 分钟的时间线：51 次定时核对里 10 次失败，都是回显服务的 TLS 握手 4 秒没完成，同时测出口本身都是通的，所以没有锁。同一时间直接经 VPN（不经 AI Anchor）请求同样三个回显服务 60 次，最慢 2.4 秒；经 AI 端口 60 次，3 次超过 3 秒；经 VPN 新建到 `1.1.1.1` 的 DoH 连接中位 0.57 秒、最慢 4.3 秒。结论：这条线路上新连接偶尔要 3～5 秒，放行时 4 秒的回显超时太紧；同时出口测试只试一次，碰巧也慢就会误锁。
- 第五版：放行时回显超时改为 8 秒（锁着时仍是 4 秒，靠并发核对尽快放行）；放行时判定“出口不可达”之前，出口测试最多试两次，两次都失败才锁。

  - 出口恢复后，请求一个不存在的 claude.ai 子域名（出口解析不了，上游代理拒绝）：归因“服务端：其余各段正常，经出口访问该域名失败”。
  - 停掉出口、等 AI 通道锁住后请求 claude.ai 和 api.anthropic.com，再请求一个普通网站：记成 1 次断联（锁住拦下，2 条，普通网站不算），归因“出口：出口不可达，AI 通道锁住；锁住 3 秒，拦下 2 次 AI 连接”。
- 测试中发现并修正：
  - 本地网络探测偶尔有一次读响应超时，同一秒的另一次探测正常；只试一次的话，会把同时发生的断联错算成“本地”。改为一次探测最多试两次，两次都失败才算失败。
  - 归因原来看整个前后 30 秒窗口里的任何失败，把 20 秒前已经恢复的出口故障算到了下一次断联头上。改为：探测失败只看断联前 10 秒到之后 15 秒；“出口不可达锁住”只在断联那一刻仍锁着时才算；网络变化、内核重启这类一次性事件仍看整个窗口。
- 真机 12 小时报告：断联 0 次，但时间线里有一次 3 分 43 秒的锁住（出口不可达）。查下来是真的断网：本地网络探测连着 7 次失败（系统 DNS 都解析不了），整条链路也失败，网卡和路由没有变化（VPN 隧道或 Wi-Fi 卡住了）。锁住期间 AI 程序发起了 58 次连接，全被拦下，内核不记错误，所以报告漏了。出口核对成功率 90.9% 也被锁住期间每 1～5 秒一次的重试拉低了；只算放行期间是 99.4%。
- 据此修改：锁住期间拦下的 AI 连接按一次锁住记一次断联并归因；报告的出口核对只算放行期间。用真机的内核日志和时间线回放新逻辑：两次断网（8 分 15 秒拦下 79 次、3 分 43 秒拦下 55 次）都归到“本地”，锁住期间本地网络和整条链路的探测全部失败；两次重装后启动核对的 2～3 秒里各拦下 2 次，归到“内核：AI Anchor 刚启动”。

  - 断联 104 次（合并了 838 条连接错误）。把间隔 5 分钟以内的算作同一起，是 22 起。

## P1b · 线路控制器（T1～T3）

- 单元测试覆盖：起始线路（固定的那条，否则优先级最高的）；探测节奏（当前线路有 AI 连接 3 秒、空闲 15 秒，其他线路 30 秒，出问题时即使空闲也按 3 秒，要求立刻探测）；当前线路失败后换到可用里最好的一条，优先级相同、延迟相近按配置顺序，明显更快的可以越过优先级；复测通了不换；旧线路恢复不回切；全部不可用只报告一次，恢复时换线并报告恢复，或当前线路原地恢复；固定或手动模式只报告一次、不换；`flaky` 换线和 2 分钟停留时间；`slow` 要持续 5 分钟、差距不够不换；手动换线、固定、取消固定；用户代理守护时线路组一律是 selector；`http://` 测速地址发给内核时协议名改成大写；`anchor line list` 的各列。
- 端到端（本机：两个 sing-box 充当两条线路，一个充当出口，python 充当 IP 回显、测速地址和“一直在输出的长回答”）：

| 用例 | 做法 | 结果 |
| --- | --- | --- |
| T1 切换线路不断回答 | 一个持续 14 秒的回答输出到第 3 秒时 `anchor line use line-b` | 回答完整（29 行全部收到）；新连接走 line-b；出口 IP 不变；时间线有一条“手动切换” |
| T2 线路物理断开 | 回答输出中停掉当前线路的服务器，同时发一个 claude.ai 请求 | 新连接 0.7～0.9 秒恢复（要求 5 秒内），换到另一条，原因 `down`；出口 IP 不变；那次断联归因“线路：线路探测失败”；在途的回答中断（预期） |
| T3 全部线路断开再恢复 | 依次停掉两条线路，10 秒后恢复一条 | 第二条停掉后 2.7 秒报告“所有线路都不可用”，只通知一次；中断期间经 AI 端口的请求失败，没有直连；恢复后 1.5 秒可用（要求 5 秒内），并通知“线路已恢复” |
| 固定线路 | `anchor line pin line-b` 后停掉 line-b，9 秒后 `anchor line unpin` | 固定期间不换线，时间线记“线路已固定，不自动切换”，经 AI 端口的请求失败；固定时 `anchor line use` 别的线路被拒绝；取消固定后 1.9 秒换到另一条 |

- 测试中发现并修正：
  - 线路一断，在途的连接跟着断、新连接立刻失败，查“此刻有没有 AI 连接”总是没有，探测反而降到 15 秒一次，换线要十几秒。改为最近 1 分钟内有过 AI 连接就按 3 秒探测，并且一记到断联就立刻测当前线路。
  - 线路断着的时候出口也测不通，AI 通道会因“出口不可达”锁住；线路恢复后要等出口核对自己的重试（锁久了 5 秒一次）才放行。改为线路一回来就请出口核对立刻重测。
  - 测速地址原来必须是 `https://`。晚高峰经 VPN 访问外网的测速地址，一半以上的探测超时，本机测试没法稳定；改为支持 `http://` 测速地址，测试里用本机地址。
- T1 的原始要求是 Claude 网页和 Claude Code 各发起一个输出 1 分钟以上的回答，这里用本机的持续输出代替；“中断期间没有直连”的原始证据是 Windows 防火墙的丢包日志，这里只验证了经 AI 端口的请求失败。真实线路（跨境中转）上还没有实测。
- 之前的回归：出口锁定 8 个场景、断联归因 3 个场景复测通过。

## P1b · 备用出口

- 单元测试覆盖：没选时用主出口；选了备用出口后出站和基线都是它自己的，`expect` 不传给内核；还没登记基线的备用出口基线为空、语言沿用主出口；选的出口不在配置里时报错，不悄悄换回主出口；备用出口必须有名字、不能重名；`anchor baseline` 把基线登记在现在所用的出口上（主出口写 `[expect]`，备用出口写它那一项，已有 `expect` 时改它的字段），别的出口的基线和文件里的注释不动；`anchor exit list` 的各列。
- 端到端（本机：两个 sing-box 充当两个出口，IP 回显服务对它们返回不同的 IP）：
  - `anchor exit use backup`：用户代理按新出口重启内核；备用出口还没登记基线，AI 通道保持锁住，经 AI 端口的请求被拒绝。
  - `anchor baseline`：测到备用出口的 IP，写进 `[[backup_exits]]` 那一项的 `expect`，主出口的 `[expect]` 不变；AI 通道放行，回显服务看到的是备用出口的 IP。
  - `anchor exit use main`：切回主出口，按主出口自己的基线核对通过；再切到备用出口，基线已登记，自动放行。
  - 用着备用出口时让它的 IP 变化：15 秒内按备用出口的基线判定“出口 IP 已变化”并锁住。
  - 不存在的出口名：报错并列出可选的名字。时间线记下每一次 `exit_switch`。
  - 切换前关闭 AI 程序：用一个命令行里带着 AI 专用浏览器配置目录的替身进程，`anchor exit use` 认出它、关掉它再切换，放行后尝试重新打开（测试里故意配了不存在的浏览器路径，如实报告“没能重新打开”）。
- 尚未实测：真实的桌面客户端（Claude 桌面版等）的关闭和重新打开；询问确认的交互（测试里都用了 `--yes`）；真机上的备用出口。

## P1b · 本地断联细分（Wi-Fi、宽带、VPN）

- 起因：真机上两次断网（8 分 15 秒、3 分 43 秒）都只能归到“本地”，因为本地网络探测也经过 VPN，分不清是 Wi-Fi、宽带还是 VPN。
- 在这台电脑上实测（全量 VPN，Wi-Fi 上网）：路由表里 VPN 网卡（Wintun，接口类型 53）有 0.0.0.0/1、128.0.0.0/1 和一条跃点 9999 的 0.0.0.0/0，Wi-Fi（接口类型 71）上有经路由器的 0.0.0.0/0，选出的上行是 Wi-Fi。ping 网关 1～6 毫秒；绑定 Wi-Fi 和连通性检测地址握手约 150 毫秒（路由表里它本来经 VPN）；绑定 Wi-Fi 直连 1.1.1.1:443 被拒或超时，所以绕开 VPN 的探测用连通性检测地址，不用公共 DNS。
- 单元测试覆盖：按路由表选上行网卡（VPN 虚拟网卡和没有下一跳的路由不算，Wi-Fi 和网线都在时按跃点）；ping 回环地址；绑定网卡连接失败时报错；按三段探测归因（路由器、换网络、宽带、VPN，没有 VPN 或没有绕开 VPN 的数据时归本地），网络变化和网络不可达在两段都正常时归 VPN，锁住拦下的同样适用。
- 端到端（本机，用户代理照常运行）：三段探测写进时间线，路由器、绕开 VPN、本机上网（目标 `vpn`）全部正常；前面三个断联场景的归因不变。测试用的出口原来用 Wi-Fi 的 DNS 解析，也会超时，改成经 DoH 解析后结果稳定。
- 真机实测 VPN 断开再连回（约 45 秒）：断开的那一秒锁住；锁住的 50 秒里路由器 5 次、绕开 VPN 上网 5 次、本机上网 6 次探测全部正常，整条链路 3 次全部失败；AI 程序的 46 次连接被拦下，记成 1 次断联，归因“VPN：网卡地址或路由有变化，Wi-Fi 和宽带正常”。VPN 连回后，最后一条网络变化通知 2 秒后核对一致放行。这台电脑的 VPN 客户端断开时不拦其他流量，绕开 VPN 的探测一直是通的。
- 真机实测 Wi-Fi 断开（2026-11-19）：关掉 Wi-Fi 约 12 秒再打开。
  - 网络变化的同一秒锁住；找不到默认网关记了一次路由器探测失败和一条“换网络”事件；断联归因“本地：连不上路由器，Wi-Fi 或网线断了”。
  - Wi-Fi 恢复后，路由器和绕开 VPN 的探测都正常，但 VPN 隧道还在却不通，持续 79 秒，没有自己恢复；手动在 VPN 客户端里断开再连接后才好，VPN 可用后 5 秒放行，一共锁住 1 分 45 秒，拦下 99 次 AI 连接。
  - VPN 重建的 8 秒里，电脑的默认路由回到了没有 VPN 的 Wi-Fi，不经代理的探测能直接上网；这段时间 AI 通道一直锁着。
  - 同一天更早还有一次 27 秒的锁住：路由器和绕开 VPN 各失败一次，8 秒后恢复，VPN 自己连回来了。
  - 这次暴露了两点，已经改掉：整个过程没有任何通知（见下面“P1c · 久未恢复的提醒”）；整段归因是“本地”，只看归因会以为 Wi-Fi 断了 1 分 45 秒，现在依据里会分开写。
- 尚未实测：真机上的宽带断开（路由器在、外网不通）。VPN 客户端如果在断开时拦着其他流量（防泄露开关），断开期间绕开 VPN 的探测也会失败，会被归成“宽带”，这种客户端上还没测过。

## P1b · direct 出口的 DNS

- 为断联归因统计 sing-box 日志时发现（约 2.5 天）：
  - AI 程序的 9,216 次连接里，1,384 次（约 15%）在 DNS 解析这一步失败，主要是 claude.ai、bridge.claudeusercontent.com、api.anthropic.com；出口核对也有 1,028 次栽在 DNS 上。
  - 原因：sing-box 的本机 DNS 用了 WLAN 网卡的两个 DNS，没有用 VPN 网卡的。一个是国内公共 DNS，路由显示它在 VPN 的“国内地址不走隧道”范围里，所以 AI 域名的查询明文经本地网络发出、绕过了 VPN；另一个是内网地址，查询进了隧道到不了，大量超时。
  - 只有 direct 出口受影响：代理型出口把域名交给出口服务器解析。
- 修复：direct 出口的目标域名改由经出口发出的 DoH 解析（`[dns] exit_doh`，默认 `1.1.1.1`，必须写 IP），优先 IPv4；线路和出口服务器自己的域名仍在本机解析。`anchor check` 的“DNS”一项按出口类型说明域名在哪里解析。
- 实测：在这台电脑上起一个绑定 VPN 网卡的 direct 出口用户代理，经 AI 端口请求 claude.ai、api.anthropic.com 等 40 次，全部拿到 HTTP 响应，中位 0.86 秒；内核日志 0 个错误、0 次解析失败，没有出现那两个 DNS 服务器的地址。
- 真机实测：装上修复后 2.7 小时，AI 程序 483 次连接、出口核对 176 次，DNS 失败都是 0，内核日志 0 个错误。修复前的 2 小时是 AI 程序 405 次连接里 14 次 DNS 失败、出口核对 191 次里 55 次。
